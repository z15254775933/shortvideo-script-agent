# 0.2.0：业务表达、审核边界与实际验证

首次提交基线为 `ec9fd7a27d6968dce753b2a3f7daf9c9223f9ea2`。提交者要求从候选人的角度继续优化。本轮实现、阅稿、修正与命令执行仍由开发 AI 完成，未代填提交者个人操作经历。

## 1. 问题和最终行为

严格文案政策能离线逐字核验，但把无害标题、开场和拍摄建议也限制在少量短语内。原正常样本多为“先看功能”“展示素材原文”，业务表达有限。

新增 `creative` 模式，作为真实运行的默认写作模式。产品事实仍保留素材原句、全部限定及逐镜引用；开场、转场、结尾与画面建议可以自由创作。平台、受众和风格进入写作指导，生成后逐项审核所有可见字段。

| 对照 | 严格模式基线 | 本轮实际创作结果 |
| --- | --- | --- |
| 标题和开场 | 四种中性标题、有限连接文案 | 抖音以字幕错字情境开场；B站以“已知／未知”组织解释 |
| 分镜 | 素材展示为主 | 明确景别、纸卡／模拟画面、人物动作 |
| 编辑和取证 | 逐镜正文与来源 | 同时展示起止时间、旁白、字幕、来源和实际检查 |
| 事实约束 | 原句、限定、引用、品牌规则及字面覆盖 | 保留原句、限定、引用和品牌规则，再独立审核自由文案，另加已观察到的高风险工作流承诺检查 |

素材依旧只有“支持字幕”“支持手动修改字幕文字”两条事实。未通过增加虚构功能、美化素材或把“未知”写成“不支持”来丰富脚本。

## 2. 审核如何工作

`grounding.py` 是业务工具实现，不是第二个 Agent：没有工具选择、规划、自动重试或终止任务权限。它使用独立对话向同一 DeepSeek 服务请求审核，生成器的对话历史和自我评价不作为审核依据。

1. 先执行素材／事实 ID、产品范围、原句与限定、引用实际出现、品牌规则及已列出的工作流承诺检查。
2. 确定性检查不通过时直接返回位置和问题，不消耗审核调用。
3. 逐项审核标题、每镜画面、旁白和字幕，必须恰好覆盖所有位置。
4. 每项返回 `supported`、`non_factual` 或 `unsupported`，支持性结论只能引用对应位置允许的事实 ID。
5. 非法来源、漏审、重复位置、格式错误、请求失败或调用超限均不能放行。可选原文回显必须与实际字段完全相同。
6. 业务 Agent 观察检查结果后自行决定改稿、重新检查或明确结束；最终成功仍受同版本检查和检索来源约束。

完整审核输入、原始可见响应、逐项结论和 token 用量保留在 Trace。Agent 只接收问题和审核摘要，减少重复上下文。审核缓存绑定需求、来源、字段、版本及审核提示的指纹，输入改变后不能挪用旧审核。

默认最多 10 次 Agent 请求、16 次工具调用、额外 4 次审核请求，总模型请求上限为 14。失败审核计数，审核器不自动重试。达到上限后不能伪装审核成功。

## 4. 保留的失败及如何修正

### 审核多返回原文导致格式失败

[首次修正运行](../examples/phase06/creative-semantic-repair/trace.json)的第一份审核响应增加了 `text` 字段，初版严格解析器拒绝，实际记录为 `semantic_review_unavailable`。该运行后来修正成功，但不算作“有效语义驳回”的主证据。

修正解析契约：可选原文回显只有与输入原文逐字相同时才接收，额外未知字段仍拒绝。重跑后得到上表的有效语义驳回记录；第一次记录没有被改写。

### 模型审核漏放了“无需重剪”类推论

[上下文精简试跑](../examples/phase06/creative-douyin-compact/script.md)被当时的模型审核放行，但开发助手阅稿发现“念错一个词……不用重剪”超出了“支持手动修改字幕文字”的来源。特别是改字幕不等于能修正音轨，不能据此承诺免去重剪或重录。

保留该次原始 `success` 结果，不将它列入通过的主验收样本。当前检查已加入 `不用重剪`、`无需重剪`、`不用重新剪辑`、`无需重新剪辑`、`不用重录`、`无需重录` 的确定性来源检查；没有对应引用原句即拒绝。回归测试确认当前审计会拒绝这条旧样本。随后重新生成了上表的最终抖音稿，并再次审核。

这项修正只覆盖明确列出的短语，仍可能误拦否定句，也不能识别全部同义表达。模型审核与生成使用同一服务，存在相关错误；独立对话不等于独立事实证明。事实性自由文案、视觉暗示和工作流推论仍是优先人工复核的内容。

精简试跑的 Agent 输入 token 为 18,454，首次创作试跑为 33,115，但两次生成内容和轮数也不同，且前者存在事实漏检，因此不据此宣称成本优化率。
