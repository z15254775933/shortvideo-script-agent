# 题目 4：短视频脚本 Agent — 需求与验收清单

日期：2026-10-28

阶段：0.2.0 交付版本。原核心链路保留，新增创作模式、独立审核与 A08—A10；本轮取舍及验证见 `docs/08-improvements.md`。

依据：用户提供的通用考试说明、GitHub 交付规范和题目 4 截图。
说明：文中“题目要求”为截图明确要求；“实施约定”为本项目建议采用的可检验定义，不额外代表出题方要求。第五步已核对全部验收样本，实际结果见 `docs/03-evaluation.md`；计划中的示例数字不等同于实测结果。

## 1. 用户、目标与成功条件

目标用户：需要根据产品资料制作短视频的内容创作者。

业务目标：输入创作要求，得到有事实依据、满足目标时长、可继续编辑的脚本；资料不足或约束无法满足时，得到明确原因及下一步所需信息。

一次任务只有同时满足以下条件，才能标记为成功：

1. 关键创作信息已经确定。
2. 输出包含标题、分镜、旁白或字幕、预计总时长、素材来源 ID、风险和任务状态。
3. 产品事实能逐项追溯到素材，表述没有扩大素材原意或遗漏必要限定。
4. 最终脚本的预计总时长不超过目标时长，且符合提供的品牌规则。
5. 时长与规则检查针对最终同一版脚本，存在可核对的实际检查结果。

实施约定：目标时长按“上限”理解，不要求严格等于目标值，也不增加题目未规定的最低占比。题目中的 30 秒目标、28 秒结果可视为这一约定的参考。

## 2. 范围与交付边界

本次核心范围：

- 接收创作输入，读取产品素材和品牌规则。
- 提供素材检索、时长估算、规则检查三个业务工具。
- 通过真实模型完成动作选择、工具调用、结果观察和后续调整。
- 输出可编辑脚本、引用、检查结果、风险及任务状态。
- 设置执行上限，保存 Trace，提供测试和可复现运行方式。

实施建议：采用 Python CLI 和本地合成素材，先完成核心链路。语言与运行方式属于实施选择，题目允许自行选择。

本次不安排视频生成、剪辑、语音合成、网页界面、线上部署、多 Agent 或生产级运行平台。外部搜索与实时产品数据接入也不作为最小版本的依赖。时长是脚本估算，不宣称等同于实际成片时长。

## 3. 输入与材料

| 输入项 | 成功前要求 | 缺失或异常时的处理 |
| --- | --- | --- |
| 主题 | 非空，能判断要表达的内容 | 请求补充，不能自行虚构产品或主题 |
| 受众 | 明确目标观看人群 | 请求补充 |
| 平台 | 明确投放平台或通用平台要求 | 请求补充 |
| 目标时长 | 有效的正数，单位为秒 | 缺失则请求补充；无效数值返回输入错误 |
| 风格 | 明确语气或表达方式 | 请求补充 |
| 产品素材 | 提供可检索资料，每条具有唯一来源 ID | 无匹配结果进入无素材处理路径 |
| 品牌规则 | 明确规则集合，可显式为空 | 为空时说明未提供额外品牌规则，事实约束仍然适用 |

实施约定：五项创作字段在成功前均需明确，最小版本不静默填入默认值。请求补充时返回缺失项及具体问题；支持用户补齐后重新运行，不要求实现持久化多轮会话。

素材记录建议包含：来源 ID、产品标识、可引用事实、适用条件或限制。为便于追溯，可为每条事实另设事实 ID。品牌规则建议包含规则 ID、说明和检查方式。

测试素材允许使用合成资料，但必须标注为合成资料。不能把合成产品描述或演示数字写成真实产品效果。

## 4. 输出契约

以下字段定义为实施约定；第二步已在 `src/shortvideo_agent/contracts.py` 确定具体命名，并在 `docs/02-solution.md` 说明。

| 输出项 | 可验收内容 |
| --- | --- |
| 标题 | 与主题、受众和风格相符 |
| 分镜列表 | 每镜有编号、画面描述、旁白或字幕、估算时长 |
| 产品事实引用 | 事实性产品描述对应来源 ID，必要时对应事实 ID |
| 预计总时长 | 与最终分镜时长之和一致，标明单位和估算方法 |
| 检查结果 | 包含时长是否通过、规则是否通过、问题及对应位置 |
| 风险 | 标明估时误差、素材限制等实际风险；没有额外风险时也有明确字段 |
| 任务状态 | 明确成功、需要补充信息或未完成，并附原因 |
| 补充请求 | 需要用户补充时列出具体信息或材料 |
| 运行关联信息 | 能关联到本次 Trace 和最终脚本版本 |

实施建议：采用结构化 JSON 作为可编辑结果，可增加易读文本输出。未完成时可以保留候选脚本，但必须标为草稿，不能将未通过检查的内容作为成功结果交付。

状态建议：

| 状态 | 使用条件 |
| --- | --- |
| `success` | 最终同一版脚本满足全部成功条件 |
| `needs_input` | 缺少关键创作信息或需要补充素材，并给出补充问题 |
| `incomplete` | 约束无法满足、工具故障未恢复或执行次数耗尽；附具体原因 |
| `invalid_input` | 无效时长、错误输入结构等不能处理的输入 |

无素材等业务情况可能以 `needs_input` 或 `incomplete` 结束，取决于模型实际决定；验收重点是动作合理、原因清楚且没有编造事实。

## 5. 工具与事实约束

### 5.1 素材检索

- 接收模型决定的检索参数，返回匹配素材、来源 ID 和可用事实。
- 没有结果时明确返回空结果；发生故障时返回可区分的错误。
- 返回内容必须足以让模型决定是否修改查询或请求补充。

### 5.2 时长估算

- 估算每镜时长和总时长，返回目标值、估算值、是否超时及超出量。
- 说明语速、停顿和必要画面占用的处理方法；方法需一致、可复现。
- 最终总时长等于最终各镜估算时长之和；计算与比较使用一致精度。
- 不能只修改总时长数字，让文本保持不变来假装修正成功。

### 5.3 规则检查

- 检查提供的品牌规则，并返回规则 ID、问题位置及问题描述。
- 检查产品事实有无素材支持，以及是否扩大了原意。
- 来源 ID 存在不等于事实成立；应核对该来源是否支持对应描述。
- 素材仅写“支持字幕”时，不能推导出“效率提升 80%”“字幕准确率 99%”或其他未提供的效果结论。这里的数字仅为禁止编造的示例。
- 允许创意画面与叙事，但不能由此新增没有依据的产品功能、数据或承诺。

实施边界：事实检查的具体实现及其语义覆盖限制须在方案和评估文档中说明；不能把简单的 ID 校验描述成完整事实核验。

## 6. 模型动态决策要求

题目要求至少实现一次“模型选择动作 → 执行工具 → 观察结果 → 模型调整下一步或结束”的循环。

需要支持的决策情形：

1. 素材检索没有结果：模型结合返回结果决定修改查询、请求补充或说明无法继续。
2. 时长检查超限：模型根据检查结果修改脚本并重新估算，或者说明无法满足。
3. 规则检查失败：模型修改有问题的表达并再次检查，或者说明无法满足。
4. 工具发生错误：模型根据错误信息选择有限恢复、其他允许动作或明确结束；不得伪造工具成功结果。

程序可以负责输入校验、工具执行、记录、执行上限和最终状态校验。依赖业务观察结果的后续动作需要由模型实际选择，固定条件分支、自动重试或预设日志不能替代模型决策证据。

实施建议：设置可配置的最大模型决策步数和最大工具调用次数。当前默认值为 10 步和 16 次（包含终止动作和无效调用），已在真实运行中验证超限返回明确未完成状态，见第五步验收报告。

## 7. 验收场景与计划证据

下表定义验收条件并标注第五步样本审核结果。最小用例覆盖五类题目必验场景，另加规则与事实核验用例。这里的通过仅指保存的样本，不是对任意输入的成功保证。

| 编号 | 场景及准备 | 通过条件 | 当前状态 |
| --- | --- | --- | --- |
| A01 | 输入完整，存在匹配素材，时长预算充足 | 输出完整脚本；引用有依据；最终估时和规则检查通过 | 通过，真实运行 |
| A02 | 缺少目标时长等关键创作信息 | 返回缺失项和补充问题；不输出伪装为成功的最终脚本 | 通过，真实运行 |
| A03 | 检索不到主题对应的素材 | Trace 中体现模型根据空结果选择改查、补充或结束；不编造产品事实 | 通过，真实运行 |
| A04 | 可控地使业务工具返回故障 | 记录实际错误和模型后续动作；恢复成功后重新满足全部成功条件，否则明确未完成 | 通过，显式故障注入＋真实模型重试 |
| A05 | 准备会触发超时的脚本或输入 | 记录实际超时检查、模型后续选择及结果；成功修正须有新版本和重新估算，否则明确失败原因 | 通过，预设初稿＋真实模型改稿 |
| A06 | 候选脚本含品牌禁用表述，或只有“支持字幕”的素材却出现无依据效果数字 | 检查能指出问题；经模型修改且重新检查通过，或明确未完成；最终不能保留无依据的产品结论 | 通过，先审稿的明确请求＋真实反馈修正 |
| A07 | 设置很低的执行步数或调用次数上限 | 到达上限即结束，返回明确未完成状态；不无限重试 | 通过，两个真实运行上限场景 |

A01—A05 覆盖题目明确要求的五类业务场景，A06 检查品牌规则和关键事实风险，A07 检查通用考试要求的执行边界。同一用例可以覆盖多个验收点。

两条真实模型执行路径的重点取证目标：

- 路径一：有素材，模型产生脚本，工具发现超时，模型修改后重新检查。是否修正成功以实际结果为准。
- 路径二：没有匹配素材，模型依据空结果调整检索或提出补充请求，最终如实返回状态。

路径是预期验证方向，不能预先写成固定动作脚本或伪造 Trace。若实际模型未触发目标分支，应调整测试输入并重新运行，保留真实结果。

已通过 C01 对检索结果做受控变化：相同共享前缀下，有资料时模型提交脚本估时，无资料时选择继续检索。两次均为真实新增单步决策，不计作两次完整 Agent 任务。映射与报告见 `data/evaluation_cases.json`、`examples/phase05/acceptance.actual.json`。

0.2.0 另增加 A08 抖音情境脚本、A09 B站解释型脚本、A10 无来源自动化宣传的独立审核与改稿，合计 11 项主验收。题目没有要求增加这些项；它们用于验证本轮改进。当前完整报告为 `examples/phase06/final-acceptance.actual.json`。

## 8. 运行记录与交付验收

每条 Trace 至少记录：

- 运行 ID、输入、运行模式、模型标识、实际配置的执行上限。
- 步骤编号、模型选择的动作、简要决策依据。
- 工具名称、实际参数、返回摘要、成功或错误状态。
- 候选脚本版本、版本对应的时长与规则检查，以及下一步动作。
- 最终输出、任务状态、结束原因、调用次数。

只保存动作的简要依据，不要求也不收集模型内部思维过程。记录中不得包含 API 密钥或隐私数据。
